# What Was Done Today - 2026-11-10

- Moved `/donationhighscore`, `/pethighscore` and `/refreshboards` from Google Sheets to PostgreSQL when `DATABASE_URL` is set. With it unset they use the sheets exactly as before, so removing that one variable rolls the bot back.
- Added the `pg` package and `src/utils/database.js`: one shared connection pool and a migration runner. On startup, before the commands load, it applies every `migrations/NNN_name.sql` file not yet listed in `schema_migrations`, in order, each in its own transaction (with an advisory lock so two bots starting together don't both run one), and logs each one it applied. A failed migration stops startup with the file's name and the database's error.
- Added `migrations/001_high_scores.sql` (`members`, `donations`, `donation_log`, `pets`, `member_pets`, `pet_log`) and `migrations/002_member_history.sql`, which adds the pet catalog's display order (`pets.sort_order`), `member_names` (every display name a member has had) and `member_stays` (each time they were in the server, with join and leave dates, so a rejoin is a second row).
- Added `src/utils/highScoresDb.js`. Each donation change saves the member, updates the total (clamped at 0 as before) and writes a `donation_log` row in one transaction. Pet changes write a `pet_log` row per pet changed. Totals are converted from pg's strings to Numbers and capped at 10 trillion GP, far inside `Number.MAX_SAFE_INTEGER`. Discord IDs stay strings.
- Added `src/utils/memberHistory.js`, which records joins, leaves and display-name changes as they happen and compares every server member with the database on startup, to catch what happened while the bot was down.
- Made `requiredEnv` and the command-loading check follow the mode: the three commands load with `DATABASE_URL` (plus their channel), or with the sheet variables when it is unset. The `/refreshboards` description says "database" instead of "sheets" when it is used.
- Added `scripts/import-sheets.js`, a one-off import of the three sheet tabs in one transaction. It is safe to run twice, warns about and skips pet keys missing from the catalog, leaves members changed by a command since the first import alone, never writes to the sheets, and prints the member count, total GP, total pets owned and catalog size next to the database's numbers.
- Added `--verify` to the import script, which re-reads the sheets and compares them with the database member by member (donation totals, pet lists, and the catalog's names, emoji IDs and order), lists each difference and exits with an error if there are any, and `--dry-run`, which imports and verifies inside a transaction that is rolled back.
- Ran the import, a second import and `--verify` on the real sheet data (37 donors, 47 collectors, 72 pets) against a throwaway in-memory PostgreSQL: 62 members, 3,124,088,063 GP and 430 pets owned matched the sheets, there were no warnings, the second import added no log rows, and verification found nothing, and found a deliberately changed total.
- Added the `migrations/` and `scripts/` folders to the Docker image.
- Added offline tests (mocked pg client) for the storage functions, the migration runner, the import, member history and the Sheets fallback being chosen when `DATABASE_URL` is unset. Also ran the migrations, storage functions and import against a real PostgreSQL engine (PGlite) outside the repo.
- Documented the Database setup, the import, the one-month sheet fallback and rollback in the README, and marked the Google variables in `.env.example` as only needed for the fallback and the import.
